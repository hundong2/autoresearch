# 01. 반복 실험의 기초

작성일: 2026-09-25 · [목차](../README.md#한국어-학습-경로)

## 다섯 필드와 Guard

“코드를 좋게 만들어 줘”는 성공을 판단하기 어렵다. Goal은 “정답을 유지하며 비교 횟수 감소”, Scope는 수정 가능한 `src/search.js`, Metric은 비교 횟수, Direction은 lower, Verify는 고정 입력 벤치마크로 정한다. Guard는 빈 입력·중복·경계값의 정답 테스트로 정한다. 단위 없는 점수와 여러 줄 표를 그대로 지표로 쓰지 않는다.

기준선은 변경 전 동일 환경에서 측정한 값이다. 후보와 기준선은 데이터, 의존성, CPU 부하, seed를 맞춘다. wall-clock 시간은 흔들리므로 여러 번 측정하고 표본을 남긴다. 커버리지가 높아도 잘못된 assertion이면 품질은 나빠질 수 있다.

## 세 가지 실행 모드

| 입력 | 의미 | 누가 실행하는가 |
| --- | --- | --- |
| Metric/Verify 포함 | Classic, 기본 25회 지표 반복 | 호스트 에이전트가 명령 계약을 해석 |
| 자연어 목표 | Orchestrator, 목표 분류·성공조건 확인 | 호스트 + 결정적 Bash 도우미 |
| 인자 없음 | 설정 질문 | 호스트의 대화 도구 |

`scripts/orchestrate.sh classify`만 실행하면 분류 문자열 하나가 나온다. 실제 에이전트가 시작되거나 소스가 수정되지 않는다. 이 차이를 알아야 도우미 테스트와 모델 종단간 평가를 혼동하지 않는다.

## 성공조건과 상태

`predicate`는 확인한 성공 명령을 고정한다. `handoff.json`은 한 명령의 결과이고 `orchestrator-state.json`은 전체 반복의 장부다. `pending_verify`는 개선을 선택할 때 쓴 평가와 별도로 독립 확인이 필요함을 나타낸다.

라우팅 우선순위는 오류 → 불안정 회귀 → 미검증 gap → 독립 verify → ship 또는 DONE이다. `DONE`이라는 문자열이 실제 코드 안전성을 보증하지 않는다. 전달한 상태값이 사실인지 확인하는 일이 먼저다.

## 작은 사고 실험

기준선 100ms, 후보 80ms지만 정답 테스트 실패라면 폐기한다. 기준선의 오래된 실패가 후보에서도 실패했다면 새 회귀는 아니지만 여전히 기술 부채다. 점수 100이어도 한 차원만 측정했다면 나머지 일곱 차원에 대한 증거는 없다.

확인 문제: 검증 코드를 Scope에 포함하면 어떤 부정 최적화가 생기는가? 모범 답: 모델이 구현 대신 평가를 약화할 수 있으므로 검증 파일과 held-out 평가를 읽기 전용으로 분리한다.
